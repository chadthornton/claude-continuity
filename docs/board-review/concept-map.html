A tracker and a wayfinder map are not on this list. A tracker is where items are stored when one workstream has too many for a list. A map is where open questions are stored when one workstream has too many for a decisions file. Neither adds a concept.

There are no lanes either. Whose call an item is lives on the item, in its gate. The review page reads the gates and sorts rows into needs you and moving without you.

A milestone is any moment with claims attached

The invite email was a UX walk, but the shape is general: a forcing event, plus a list of sentences that must be true when it arrives. Five kinds fit.

A real-world event
Three guests join the Tokyo trip on 2026-11-07. Claim: a guest with no account can open the invite on a phone and add a place.
A release
Plugin 0.15 ships. Claim: a project with no review page gets one on its first run.
A cutover
Lists move to the new model. Claim: no code reads places.list_id.
An evidence checkpoint
The first multi-person trip ends. Claim: every open research question has an event count beside it. Trip-planner's social-decisions-review workflow already waits on this trigger.
A quality bar
Before inviting anyone outside the family. Claim: every screen is usable at 390px.

Not a milestone: an area you keep investing in (that is a workstream), a single task (an item), or a date with no claims (a deadline).

The practices this encodes

What you are already doing

  • Writing the outcome before the work. The email was the spec, and each sentence became a check.
  • Rehearsing on the real thing. The first rehearsal found three phone layout bugs that no plan listed.
  • Keeping few things in flight. The close-out took the board from 29 rows toward 8.
  • Recording why. Every decision carries its reason.

Three things I would add

  • Each workstream names the bet it serves. This is the one link missing today, and it is the one that makes drift visible.
  • Each milestone has a forcing event outside the codebase. A person, a date or a release. Without one it is a wish list.
  • Closing a milestone includes one look back. Which claims were wrong as written, and which bet that touches.

What a reviewer could check once the links exist

The diagram's arrows are four fields in the board file: which bet a workstream serves, whether a row is a milestone, the milestone's claims with their evidence, and which claim an item is for. With those written down, the board is a small graph that fits in a few kilobytes.

A script can find

  • A workstream that serves no bet.
  • A bet with no live work behind it.
  • A claim marked true with no evidence.
  • A false claim with no item aimed at it.
  • Open items that serve no claim while a milestone is open.
  • Build items moving ahead of an open question that gates them.

A reviewing Claude can judge

  • Two workstreams solving the same problem under different names.
  • A decision that contradicts the principle it cites.
  • A bet that no longer describes what is shipping.
  • A connection across workstreams nobody has drawn.

The reviewer reads the script's findings and the compact graph, then writes a short reflection as a section on the review page, where you can reply to it. It reads the graph, never the full 118 KB board.
